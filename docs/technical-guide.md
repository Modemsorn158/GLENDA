# Technical guide: running and reproducing GLENDA

This research rebuild includes development-fold experiments, short tuning, a final fit and a one-time internal holdout evaluation. At the fixed threshold the model missed 55 of 75 positive holdout frames; only three known groups contributed negative frames, and patient-level independence is not guaranteed. The project is for research only and does not support clinical use. The original data are kept separately in `../read_only/raw` and are never modified by the audit. See the [research report](../reports/research_report.md), [methodology](methodology.md) and [literature notes](literature.md).

The project software is distributed under the [MIT License](../LICENSE). This does not grant rights to the GLENDA dataset, images derived from it, or third-party pretrained weights: their own terms apply. The dataset is restricted to non-commercial scientific research and requires attribution, as described below. The current checkout omits the dataset and model checkpoints, but older Git commits contain dataset images; see the [image-handling guidance](data_privacy.md).

GitHub Actions is configured to run CPU tests on Windows and Linux, using synthetic data without downloading the research dataset or pretrained weights. The local commands below also run them. Image and checkpoint files are broadly ignored to reduce the risk of accidentally committing medical data; any future exception for an approved, non-sensitive figure should be narrow and reviewed.

The [artifact manifest](../reports/artifact_manifest.json) records hashes from the study's public summaries without publishing private images, predictions, or checkpoints. Run `python -m glenda.artifact_manifest` to reconstruct it, or add `--verify-local` to check available local study artifacts against the recorded hashes without evaluating the holdout again. These hashes do not establish patient independence or provide the private artifacts needed to reproduce the study.

**Historical results and new studies:** The completed study used the training code and artifacts identified in its recorded source hashes. Frozen-block behavior and provenance requirements have since changed; the old threshold artifact lacks the newly required epoch-history hashes and cannot be used to launch a new final fit. Do not regenerate a threshold against the consumed holdout. See the [next-study protocol](next_study.md) for the independent data, patient mapping, calibration, and prespecified operating requirement still needed.

The later [extended development comparison](../reports/deep_development_results.md) trained frozen, partially fine-tuned and fully fine-tuned models across five development folds. Its adaptive validation scores are exploratory and do not change the completed holdout result or provide independent validation.

For a new study, obtain the expected inventory and candidate-pair SHA-256 values from separately trusted audit records. The examples below use the PowerShell variable `$TrustedInventorySha256`; set it and `$TrustedCandidatesSha256` from those records before running them. These command-line tools verify the relevant image partition against the inventory before use; a random-initialized single-fold smoke test may omit the inventory arguments. Image verification takes time and cannot prevent a later file change. The training, cross-validation, final-fit and evaluation Python entry points also require these inputs; the private `_synthetic_test_only` bypass is exclusively for generated test fixtures, not real studies. The existing holdout is already consumed and must not be evaluated again.

After auditing a new dataset, record the SHA-256 of its inventory separately from the writable working copy, for example in a signed or access-controlled study record with the audit date, dataset version and reviewer. PowerShell can calculate the initial value with `(Get-FileHash outputs\audit\inventory.csv -Algorithm SHA256).Hash.ToLower()`. Also record the candidate file digest with `(Get-FileHash outputs\audit\near_duplicates.csv -Algorithm SHA256).Hash.ToLower()` after the candidate review is frozen, and preserve both values independently. Preserve those values through the study; recalculating a digest from an already modified inventory does not establish integrity. Retrieve them from the trusted record and set `$TrustedInventorySha256` and `$TrustedCandidatesSha256` to the corresponding 64-character values. The manifest must cover the study-specific trusted inventory exactly, and group IDs must match the canonical connected components. The prior study's trusted inventory digest is recorded in [archive_check.json](../reports/archive_check.json), but its artifacts lack the new integrity metadata and cannot be retroactively verified as a new experiment. Use a newly audited dataset, new paths and an independent holdout for a future study. See [study provenance](study-provenance.md) for the limited historical source mapping.

## Dataset inventory

Install Python and the project training dependencies (`python -m pip install -e '.[training]'`), then run from this directory (PowerShell). Inventory and archive checks alone require Pillow; the full test suite also requires PyTorch, torchvision, scikit-learn and Matplotlib.

```powershell
$env:PYTHONPATH='src'
python -m glenda.inventory ..\read_only\raw outputs\audit
python -m glenda.archive_check outputs\audit\inventory.csv ..\read_only\zip\Glenda_v1.5_classes.zip ..\read_only\zip\GLENDA_v1.5_no_pathology.zip ..\read_only\raw outputs\audit\archive_check.json
python -m unittest discover -s tests -v
```

The recorded GPU environment used Windows x64, Python 3.14.7 and CUDA-enabled PyTorch 2.15.0+cu132. With a compatible NVIDIA driver and that Python version installed, the following PowerShell commands create a separate environment and check its dependencies and GPU availability:

```powershell
py -3.14 -m venv .venv-reproduce
.\.venv-reproduce\Scripts\python.exe --version
.\.venv-reproduce\Scripts\python.exe -m pip install -r requirements-gpu.lock --extra-index-url https://download.pytorch.org/whl/cu132
.\.venv-reproduce\Scripts\python.exe -m pip install -e . --no-deps
.\.venv-reproduce\Scripts\python.exe -m pip check
.\.venv-reproduce\Scripts\python.exe -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
```

Confirm the version output is Python 3.14.7 and that CUDA availability is `True`. The lock records versions, not package hashes; the extra index may serve packages from more than one source. It does not guarantee package integrity or bitwise reproducibility, and other platforms may require different builds. A CPU environment is sufficient for smoke tests. These commands describe a clean setup; they do not rerun the completed study.

The inventory checks positive images against the supplied COCO file, decodes every frame, records SHA-256 hashes, and reports exact duplicates and unreadable files. The archive check compares those frame hashes and the COCO JSON with the supplied ZIPs; the local check matched all 13,811 frames and the COCO JSON. It does not verify every ancillary archive file. Derived files go in `outputs/`, which is ignored by Git. To screen cross-component near duplicates and create a development/test manifest, install the project dependencies (`python -m pip install -e .`), then run:

```powershell
python -m glenda.near_duplicates ..\read_only\raw outputs\audit\inventory.csv outputs\audit\near_duplicates.csv
python -m glenda.exploration outputs\audit\inventory.csv outputs\audit\composition.png
python -m glenda.make_splits outputs\audit\inventory.csv outputs\audit\near_duplicates.csv outputs\splits\v1
python -m glenda.rebalance_development outputs\splits\v1\manifest.csv outputs\splits\v2
```

The splitter refuses to overwrite a previous manifest. It joins case IDs, video IDs, identical image hashes, and all candidate pairs from the near-duplicate screen transitively. The latter is conservative: perceptual-hash matches may be false positives. The screen detects only pairs within Hamming distance three on a 64-bit difference hash; it does not prove absence of similar images. The first manifest creates an outer holdout using a shuffled stratified-group fold. After feasibility work showed that one development fold had only one negative-containing group, v2 reassigned development groups to balance negative-group counts while preserving every held-out row exactly. It records source hashes, seeds and class/group counts. V1 feasibility results and v2 tuning results use different development folds and must not be treated as paired. No claim of patient-level independence is possible for negative videos with unknown cases. **A split must not be treated as a valid locked test if researchers have used its labels or images to make subsequent modeling choices.** The previous research used this dataset, so none of its partitions are external validation.

The official [GLENDA v1.5 documentation](https://ftp.itec.aau.at/datasets/GLENDA/) identifies annotated endometriosis frames and sequences with no visible endometriosis-related pathology as binary classification sources. The release is restricted to non-commercial scientific research and requires citation of Leibetseder et al., *GLENDA: Gynecologic Laparoscopy Endometriosis Dataset*, MMM 2020, [doi:10.1007/978-3-030-37734-2_36](https://doi.org/10.1007/978-3-030-37734-2_36).

## Critical limitations

Case IDs are present in positive filenames. Some negative videos match positive videos and inherit their known case ID. The remaining negative videos lack a case mapping, so grouping by available case/video IDs cannot guarantee patient independence. Seek authoritative case metadata before interpreting patient-level generalization. Exact-duplicate checks alone do not rule out near-duplicate leakage. The dataset's curated frame prevalence is not clinical prevalence. Prior reported scores remain unverified; the new holdout result is internal and not externally validated.

## Development-fold training (experimental)

Install the optional training dependencies with `python -m pip install -e '.[training]'`. For a new study, replace the historical example paths with the new dataset and output paths. A development fold can be run with `python -m glenda.train_fold ..\read_only\raw outputs\splits\v2\manifest.csv outputs\runs\fold0 --fold 0 --inventory outputs\audit\inventory.csv --inventory-sha256 $TrustedInventorySha256 --candidates outputs\audit\near_duplicates.csv --candidates-sha256 $TrustedCandidatesSha256`. Defaults use ImageNet EfficientNet-B0 with frozen features, AdamW and validation average precision for early stopping. `--fine-tuning partial` or `full`, `--weighted`, and `--architecture resnet50` change the comparison. Run all folds for a configuration before comparing it. Pretrained weights may require a download. Inputs are resized to 224 by 224 (changing aspect ratio), with a horizontal flip during training and ImageNet normalization. This is a starting transformation, not an established clinically optimal preprocessing policy.

The command never evaluates the test partition. It records configuration, manifest hash, epoch losses, validation average precision and the best checkpoint, and refuses to overwrite an existing run. The prespecified short tuning comparison can be started with `python -m glenda.cross_validate ..\read_only\raw outputs\splits\v2\manifest.csv configs\tuning.json outputs\search\tuning_v2 --inventory outputs\audit\inventory.csv --inventory-sha256 $TrustedInventorySha256 --candidates outputs\audit\near_duplicates.csv --candidates-sha256 $TrustedCandidatesSha256`. This runs five folds per configuration and records fold failures; rerunning the command skips completed or failed folds. New searches record training-source hashes and stop if the code changes between folds. The earlier feasibility runs predate this check. Interrupted and failed folds are retained for inspection rather than silently retried. The original v1 tuning attempt was interrupted after the fold imbalance was discovered; its artifacts remain in `outputs/search/tuning/`.

After all tuning folds complete, `python -m glenda.select_candidate outputs\search\tuning_v2` freezes the EfficientNet trial with the highest mean development AP. Then use `python -m glenda.select_threshold outputs\splits\v2\manifest.csv outputs\search\tuning_v2\trial_001 outputs\search\tuning_v2\selected_threshold.json`, substituting the selected trial directory for a new study. It selects a pooled out-of-fold F1 threshold and checks fold completion, exact development coverage, labels, groups and manifest identity. Threshold selection on the same predictions is optimistic, and must not be reported as independent performance. Fold scores also drive early stopping and model selection, so they can be optimistic.

After model and threshold selection, `python -m glenda.fit_final ..\read_only\raw outputs\splits\v2\manifest.csv outputs\search\tuning_v2\trial_001 outputs\search\tuning_v2\selected_threshold.json outputs\final\selected --inventory outputs\audit\inventory.csv --inventory-sha256 $TrustedInventorySha256 --candidates outputs\audit\near_duplicates.csv --candidates-sha256 $TrustedCandidatesSha256` fits on all development frames; substitute the selected trial directory for a new study. It uses the median of the five validation-selected best epoch counts, fixes the selected threshold, verifies fold configurations and prediction hashes, and never opens test images. This study's final fit used one epoch, the median of the five selected epoch counts.

Only after the model, fixed epoch count and threshold are selected and final fitting is complete, run `python -m glenda.evaluate_test ..\read_only\raw outputs\splits\v2\manifest.csv outputs\final\selected\final.pt outputs\test\selected outputs\test\ledger --inventory outputs\audit\inventory.csv --inventory-sha256 $TrustedInventorySha256 --candidates outputs\audit\near_duplicates.csv --candidates-sha256 $TrustedCandidatesSha256`. The command reads test image bytes for integrity verification before creating a ledger entry keyed by held-out paths; it creates the entry before model inference, and refuses a second evaluation of the same holdout through the same ledger, even if development folds change. Keep that ledger for every evaluation; this is a workflow safeguard, not a security barrier. An interrupted run leaves the entry marked `started`; investigate and document the reason before any retry. The output includes predictions, classification metrics, Brier score, fixed-threshold sensitivity, cluster-bootstrap intervals, ROC, precision-recall and calibration plots, plus a local contact sheet of up to eight highest-scoring false positives and eight lowest-scoring false negatives. That sheet contains derived medical images and must remain private. Bootstrap clusters reflect only known linked groups, so their intervals cannot account for unidentified patient overlap. Do not use test sensitivity analyses to change the threshold. The full evaluation and report path was exercised with synthetic data and a random checkpoint before the real holdout was evaluated.

The example study has already consumed this holdout and its ledger entry is retained. The command is documented for auditing and future independent studies, not for iterative re-evaluation of this test set. Its recorded results are in [test_results.md](../reports/test_results.md).

For new evaluations, the completed ledger records hashes of all result files and both reporting commands verify them. Keep the ledger access-controlled: hashes in a writable ledger are not signatures. An interrupted evaluation leaves a started entry; preserve the files and investigate before any authorized recovery. Historical ledgers lack these hashes; only for archival reporting, `--allow-legacy-unverified` explicitly acknowledges that limitation. It does not recreate missing historical integrity evidence. After successful completion, `python -m glenda.summarize_test outputs\test\selected outputs\test\ledger reports\test_results.md` generates a de-identified result table from the recorded metrics and verifies the ledger. The full prediction and image files stay in the ignored `outputs/` directory.

For a research-only demonstration, install `python -m pip install -e '.[training,demo]'` and run `python -m glenda.demo outputs\final\selected\final.pt --allow-legacy-checkpoint` for the historical checkpoint. The flag acknowledges that the old checkpoint lacks the new preprocessing contract; it does not certify compatibility. New checkpoints carry an inference contract and do not need the flag. The demo listens on localhost, displays the fixed threshold and an uncalibrated score, and is not for diagnosis. A below-threshold result does not rule out pathology. Follow the [image handling guidance](data_privacy.md).

Each demo session creates a `gradio_uploads_...` directory next to the checkpoint and attempts to remove it when Python exits normally or unwinds after a handled exception. Abrupt termination can leave files behind: this occurred in a local synthetic test. Inspect that checkpoint directory after use and manually remove only session directories you recognize; older versions also used `gradio_tmp`, which the new code does not automatically delete. OS or library caches and other copies are outside this cleanup, secure erasure is not guaranteed, and localhost does not itself provide access control. Use only appropriately authorized, de-identified images. The Gradio 6.32.0 interface was checked end-to-end with a synthetic image; the prior wording was also checked with one development image. Neither check is an additional test-set evaluation.

After stopping the demo, open `outputs/final/selected` in File Explorer and inspect any `gradio_uploads_...` directories. Delete a directory only after confirming its contents are no longer needed. The earlier verification also left a legacy `outputs/final/selected/gradio_tmp` directory; inspect it separately. This is ordinary file deletion, not a guarantee of secure erasure or a complete retention policy.

The [development-only threshold-transfer diagnostic](../reports/threshold_stability.md) measures how thresholds chosen from four saved development folds behave on the fifth. It is exploratory: model selection used all folds, and the models producing the other-fold scores were trained on the target fold. It is not an independent or nested performance estimate, does not validate transfer to the final refit and does not replace an external cohort. It does not change the selected threshold or use holdout predictions.

To reproduce it without overwriting the existing report, run `python -m glenda.threshold_stability outputs\splits\v2\manifest.csv outputs\search\tuning_v2\trial_001 outputs\search\tuning_v2\selected_threshold.json outputs\review\threshold_stability.md`.

The project does not implement epoch-level checkpoint resumption. GPU kernels are not guaranteed deterministic. Do not present smoke tests as research results. The study's held-out evaluation has already been run once; do not reuse it for model or threshold selection.
